# 新需求设计与防屎山计划书模版 (Plan Mode Spec)
> 适用于：向 AI 提出新功能、重构或改版需求时。
> 核心原则：**设计期查重、锁定改动半径、先确认后编码、Proof 驱动验证**。

---

## 1. 需求意图 (Intent)
- **目标**：一句话说明这个需求要做什么，解决什么用户痛点。
- **非目标 (Out of Scope)**：本次绝对不改动什么、不引入什么（圈定边界，防止 AI 发散）。

## 2. 存量资产查重 (Existing Assets Check - 严防平行实现)
> **AI 必须在写代码前全局 grep / 检索并在此回答：**
- [ ] **已有工具函数 / API**：项目中是否已有类似功能的函数？（有：`path/to/util.ts#fn` / 无）
- [ ] **已有组件 / 视图**：是否有可复用或扩展的 UI 组件？（有：`path/to/Component.tsx` / 无）
- [ ] **数据源与类型定义**：该业务概念是否有已存在的 Schema / Type / Store？（声明对应源头）
- **结论**：复用已有资产，还是确定需要新建？若需新建，为何现有资产无法满足？

## 3. 拟改动文件清单 (Blast Radius)
明确限制改动范围，禁止触碰范围之外的代码：
```
新增文件：
- path/to/NewComponent.tsx (说明为什么不能在已有组件内扩展)

修改文件：
- path/to/ExistingStore.ts (只增量追加 action，不修改现有行为)
- path/to/Router.tsx (接入路由)

受保护/严禁改动文件：
- path/to/core/... (核心逻辑，本次不涉及)
```

## 4. 实施顺序 (Order of Work)
1. 扩展现有共享类型/模型。
2. 实现核心逻辑/API 层，并配套单元测试。
3. 接入 UI/调用层，复用项目全局 Design Token。
4. 运行全量静态检查与现有测试集。

## 5. 验收证据 (Proof)
- [ ] 自动化测试：执行命令 `...`，先失败后通过。
- [ ] 视觉与交互证据：真实页面/弹窗渲染无错位、无遮罩丢失（附截图或浏览器验证日志）。
- [ ] 零残骸确认：没有留下未引用的旧文件、无注释掉的遗留逻辑。
